# 운영실 — 적용 및 검증 기록

## 범위

- `admin.html`: 휴대폰·PC 운영자 웹. 일반 앱과 별도 로그인 저장소, MFA 필수.
- 운영 현황, 버그/신고/보안 제보, 공유 글과 사진·댓글, 사용자 검색, 광장 제한, 계정 정지·영구 제한·삭제, 개인/전체 앱 내 알림, 오류 및 운영 기록.
- **개인 공간의 비공개 기록·일기·독서록·아이디어·가계부와 비공개 사진을 읽는 기능은 없다.** 사용자가 2026-10-07에 비공개 열람 제외를 최종 결정했다.
- 운영자 계정은 사용자가 지정한 `wnghwngh01@gmail.com`. 실 DB에서 확인한 UID는 `d099abb9-8d20-4c52-a176-dada5fe77e01`이며 이메일 인증 완료 상태였다. 2026-10-08 사용자 명시 승인 후 이 계정 하나에 운영자 권한을 부여했다.

## 적용 순서 (서버·테스트 웹 배포 완료)

1. Supabase `kplhezgrxuiuswsbhpdw`에 step13 → step14 → step15 SQL을 순서대로 한 번 적용한다. 먼저 백업/복구 지점을 확보하고 트랜잭션 실패 시 이후 단계를 진행하지 않는다.
2. `operator-account` Edge Function을 배포한다. Supabase 기본 서버 환경 변수만 사용한다. 서비스 키를 브라우저 파일에 넣지 않는다.
3. `operator_owner.sql`로 위 계정 하나를 등록한다. 계정 UUID와 이메일 인증 상태가 일치하지 않으면 중단한다. 별도 운영자 회원가입은 없다.
4. 일반 앱의 버그 제보 및 알림함 변경과 운영실을 함께 웹 배포한다. Android APK는 별도 작업이다.
5. 운영자는 `admin.html`에서 기존 이메일/비밀번호로 로그인하고, 본인이 인증 앱에 QR을 등록한 뒤 MFA를 완료한다. 비밀번호·OTP·QR 비밀값을 작업 기록에 남기지 않는다.
6. 승인된 테스트 계정으로 제보 → 운영자 조회 → 개인 답변 → 사용자 알림 조회·읽음 유지, 공유 글 숨김/복구, 제재/해제 흐름을 확인한다. 실제 사용자를 시험 제재·삭제하지 않는다.

## 권한과 제재

- 일반 사용자는 운영자 RPC 실행 시 서버에서 거부된다. 운영자도 `aal2` 없이는 데이터에 접근할 수 없다.
- 광장 제재는 테이블 트리거에서 적용하여 기존 SECURITY DEFINER 글쓰기 RPC에도 적용한다.
- 계정 정지는 Auth ban과 별도로 PostgREST 요청 전 검사 및 Storage 제한을 적용한다. 기존 요청 전 hook이 있으면 덮어쓰지 않고 SQL이 실패하도록 했다.
- 삭제 전 계정을 차단하고, 사용자 소유 경로의 파일을 지운 뒤 Auth 계정을 삭제한다. 중간 실패는 감사 기록에 남고 차단을 유지한다. 일부 삭제는 복구할 수 없으므로 운영자가 확인 후 재시도한다.
- 운영실에서는 운영자 자신의 계정을 제재하거나 삭제할 수 없다.
- 게시물 숨김은 **광장 노출 제한**이다. 이미 공유된 공개 사진 URL을 회수하거나 기존 다운로드를 삭제하는 기능은 아니다. 원본 사진을 자동 삭제하지 않는다.
- 신고 시점부터 글/댓글 텍스트와 공개 사진 경로의 사본을 보관한다. 과거 신고의 당시 내용은 복원하지 않으며 사진 파일 자체는 별도 복제하지 않는다.
- 전체 알림은 앱 내 알림이다. OS 푸시·예약 발송은 이번 버전에 포함하지 않는다.

## 로컬 검증과 실서버 검증 구분

- `node tests/operator-console-behavior.mjs`: PGlite(PostgreSQL WASM), 로컬 스키마 fixture로 마이그레이션과 역할별 허용/차단, 제재, 알림 분리 등을 검증한다. Supabase Auth/Storage/실제 PostgREST hook 종단 테스트는 아니다.
- `node scripts/preview-operator.mjs`: `http://127.0.0.1:4174/admin-preview.html`은 **샘플 데이터**로 화면만 검증한다. 실제 데이터 저장을 하지 않는다. `admin.html` 경로는 실제 설정을 사용한다.
- 390×844 모바일에서 제보 상세, 목록, 화면 가로 넘침 없음(문서 375px / viewport 390px)을 확인했다. 최초 메뉴 때문에 생긴 가로 넘침과 상세 닫기 버튼 줄바꿈을 수정했다.
- 전체 기존 검사와 신규 SQL·서버 함수 검사 총 23개 파일 및 웹 빌드가 통과했다. 서버 함수 Auth/Storage 검사는 모의 환경이며 실제 사용자 로그인 이후 종단 검증은 남아 있다.
- 실 Supabase에 step13~15 및 owner SQL 적용 성공, operator-account 서버 함수 배포를 확인했다. 2026-10-09 읽기 전용 재검증에서 운영자 1명, 지정 UID 일치, MFA 필수, admin_private 테이블 전체 RLS, 일반 사용자 스키마 접근 차단 및 요청 hook 설정을 확인했다. 실제 HTTP 익명 요청에서 운영자 조회 RPC와 계정 함수 모두 401을 반환했다. 실제 계정 제재·삭제·알림 발송은 수행하지 않았다.

## 장애 시 복구

- 새 웹 버전을 이전 커밋으로 되돌려도 신규 테이블은 보존한다. 기존 개인 자료는 건드리지 않는다.
- 서버 요청 hook 자체에 오류가 있으면 SQL Editor에서 `alter role authenticator reset pgrst.db_pre_request; notify pgrst,'reload config';`로 해제할 수 있다. 이 동안 기존 세션 차단 보장이 약해지므로 운영자 제재 기능도 중지한다.
- 공개 피드 원본 함수는 `admin_private` 스키마에 보존한다. wrapper만 제거하고 해당 함수를 원래 스키마로 이동하면 복원 가능하지만, 함수별 기존 권한과 적용된 숨김 상태를 먼저 확인한다. 데이터 보존을 위해 `DROP ... CASCADE`로 일괄 삭제하지 않는다.
- 롤백이나 권한 추가는 운영 환경과 현재 migration 상태를 다시 확인한 뒤 수행한다.
